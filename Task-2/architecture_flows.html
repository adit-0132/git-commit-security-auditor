Tenant Isolation Middleware resolves tenant from subdomain, injects into JWT. Postgres RLS policy filters every query by tenant_id — no application-level WHERE clauses needed.
SP Cross-Tenant Queue SPs have global identity (no tenant scope). A separate sp_visibility RLS policy grants read access to orders from linked distributors only — isolation holds everywhere else.
RBAC Enforcement JWT carries tenant_id + role. DRF permission class checks role predicates per endpoint. A sales_rep from Distributor A physically cannot authenticate against Distributor B's tenant context.
Sync vs Async Stripe webhooks return 200 in <300ms — processing is always queued. Outbound calls (email, WhatsApp, label gen, Sage) are fully async. Only Stripe Checkout redirect is synchronous.
02

Three Business Flows → Shared Pipeline

Online checkout and B2B quotation converge into one fulfillment pipeline

flowchart TD subgraph Flow1["Flow 1 — Online Checkout"] F1A["Customer visits distributor storefront"] F1B["Canvas customizer → Stripe Checkout hosted page"] F1C["Stripe webhook received\nSignature verified · Event persisted for idempotency"] F1D["Payment recorded via async task\nOrder auto-created · source = online_checkout"] end subgraph Flow2["Flow 2 — B2B Quotation"] F2A["Sales rep builds quote\nProducts · pricing · artwork upload"] F2B["Quote emailed to customer via SendGrid"] F2C["Customer logs into portal\nThreaded comments → approve or reject"] F2D["Approved quote converts to order\nsource = b2b_quote · same model as Flow 1"] end subgraph Pipeline["Shared Fulfillment Pipeline — both flows enter here"] P1["Order created\nstatus: pending_artwork\nPayment status derived from cleared payment rows"] P2["Artwork uploaded to S3\nAdmin + customer review loop\nReal-time threaded comments via WebSocket"] P3["Artwork approved → domain event emitted\nPO PDF generated and emailed to supplier"] P4["Supplier assigned\nstatus: po_sent"] end subgraph Flow3["Flow 3 — Service Provider Execution"] F3A["SP logs in — JWT carries sp_id, no tenant scope\nUnified queue shows orders from all linked distributors\nRLS sp_visibility policy enforces link-only access"] F3B["SP accepts order → in_production\nProduction progress updated incrementally"] F3C["Leg 1: Supplier ships to SP\nTracking number entered manually · status: leg1_shipped"] F3D["Leg 2: SP generates Shippo label\nCustomer notified via email + WhatsApp · status: leg2_shipped"] F3E["Shippo tracking webhook fires on delivery\nCustomer delivery notification enqueued\nstatus: delivered"] end F1A --> F1B --> F1C --> F1D --> P1 F2A --> F2B --> F2C --> F2D --> P1 P1 --> P2 --> P3 --> P4 P4 --> F3A --> F3B --> F3C --> F3D --> F3E
Unified Order Model A single Order model handles both origins. A source field (online_checkout vs b2b_quote) distinguishes them. The entire fulfillment pipeline — artwork approval, PO generation, SP execution — is identical for both.
Multi-Mode Payments Stripe, bank transfer, cheque, and cash are all recorded as Payment rows. Partial payments are supported — order payment_status is derived from the sum of cleared rows, not a single field.

Graceful Degradation Every external call sits behind a circuit breaker. SendGrid fails over to SES. WhatsApp is explicitly best-effort — orders still flow if WATI is down. Shippo failures page ops, not the customer.
Webhook Safety Stripe and Shippo webhooks are verified, persisted to DB with a processed_at idempotency key, then enqueued. The view always returns 200 fast — processing happens entirely out of band.
