WAF on CloudFront only WAF is attached to CloudFront, not the ALB. The ALB's security group only allows traffic from the CloudFront managed prefix list, so all requests pass through WAF before they can reach the load balancer. Attaching WAF to both would double the cost with no security benefit.
PgBouncer on EC2, not ECS PgBouncer runs on an EC2 pair (one per AZ) rather than as an ECS sidecar. As a sidecar, each Fargate task would maintain its own isolated pool — defeating the purpose. A shared EC2 pair aggregates all Fargate task connections into a single pool of 200 connections to RDS, regardless of how many tasks are running.
Redis — 3 shards for 3 roles Celery broker, Django Channels WebSocket layer, and tenant resolution cache are separated into three Redis shards. This prevents a spike in Celery job volume from starving WebSocket connections, and keeps cache eviction policies independent per use case.
NAT Gateway per AZ One NAT Gateway per AZ rather than sharing one. Cross-AZ NAT traffic is billed per GB. With ECS tasks spread across both AZs, a single NAT in AZ-a would incur data transfer charges for all AZ-b egress. Two NATs is cheaper at scale and eliminates a cross-AZ availability dependency.
VPC Endpoints for S3 + SQS S3 and SQS traffic routes through VPC Gateway/Interface Endpoints rather than through the NAT Gateway. NAT Gateway charges $0.045/GB of processed data — S3 uploads and SQS polling at scale would make this expensive. VPC Endpoint traffic has no per-GB charge.
Beat Service — pinned at 1 Celery Beat must run as exactly one instance. If two Beat processes run simultaneously, every scheduled job fires twice. The ECS service desired count is pinned to 1 and autoscaling is explicitly disabled. The schedule itself is stored in Postgres (DatabaseScheduler) so it survives task restarts without losing state.

Network Security Zones

What lives in public vs private subnets, and why

flowchart LR subgraph PublicSubnet["Public Subnets — internet-reachable"] ALB2["ALB\nTerminates TLS\nRoutes to private compute"] NAT["NAT Gateways\nEgress-only for private subnets\nNo inbound path"] end subgraph PrivateCompute["Private Compute Subnets — no internet route"] API2["ECS API Tasks"] Workers2["ECS Worker Tasks"] Beat2["ECS Beat Task"] PgB2["PgBouncer EC2"] end subgraph PrivateData["Private Data Subnets — compute only, no internet"] RDS2["RDS Postgres\nNo public endpoint"] Redis2["ElastiCache Redis\nNo public endpoint"] end subgraph AWSServices["AWS Services — via VPC Endpoints"] S3E["S3"] SQSE["SQS"] SME["Secrets Manager"] ECRE["ECR"] end subgraph ExternalAPIs["External APIs — via NAT Gateway"] Stripe2["Stripe"] SendGrid2["SendGrid / SES"] WATI2["WATI"] Shippo2["Shippo"] Sage2["Sage"] end Internet([Internet]) --> ALB2 ALB2 --> API2 API2 & Workers2 --> PgB2 --> RDS2 API2 & Workers2 & Beat2 --> Redis2 API2 & Workers2 --> S3E & SQSE & SME & ECRE Workers2 --> NAT --> ExternalAPIs
Private subnets have no internet route ECS tasks, PgBouncer, RDS, and ElastiCache all sit in private subnets with no internet gateway route. The only path out is through the NAT Gateway, and only workers that need to call external APIs use it.
Data subnets locked to compute only RDS and ElastiCache security groups only accept connections from the compute subnet's security group — not from the public subnet. Even if the ALB were misconfigured, it could not reach the database directly.

CI/CD Pipeline

From code push to running ECS task

flowchart LR GH["GitHub\nPR or main branch push"] GHA2["GitHub Actions\ntest → ruff lint → bandit security scan\nbuild Docker image → push to ECR"] ECR2["ECR\nImmutable SHA tag\nVulnerability scan on push"] Migrate["One-off ECS Task\npython manage.py migrate\nRuns before service rollout"] Deploy["ECS Rolling Deploy\napi + worker services\nBlue/green for schema-risky releases"] Live["Live ECS Tasks\nPick up new image on next task replacement"] GH --> GHA2 --> ECR2 --> Migrate --> Deploy --> Live
Migrations before rollout Database migrations run as a one-off ECS task before the new service version is deployed. This means the old code runs against the already-migrated schema briefly during rollout — migrations must always be backward-compatible with the previous release.
Blue/green for risky changes Standard releases use rolling deploy (zero downtime, gradual task replacement). Schema changes that are not backward-compatible use blue/green — the new version is fully started before traffic is cut over, with automatic rollback if health checks fail.
