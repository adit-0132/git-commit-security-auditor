Security Review: Commit 07b44e26

Hey Mudit, good progress on the Dashboard/Settings features! However, this commit has two serious security issues that need to be fixed before this code goes anywhere near a shared repo or production. Let me walk you through both.

Issue 1: Hardcoded Placeholder Secret Key [HIGH]

File: backend/utils/security.py, line 6

# ❌ What you have
SECRET_KEY = "your-secret-key-change-in-production"

Why This Is Dangerous

This string is almost certainly used to sign session tokens, JWTs, or CSRF tokens in your backend. Because it's a well-known placeholder value, an attacker could use this exact string to forge valid authentication tokens — essentially logging in as any user, including admins, without a password. Even if you planned to "change it later," committing it means it's now in Git history forever, even after you change it.

Real-world scenario: An attacker finds your public GitHub repo, sees this key, and uses it to sign a JWT claiming to be user_id: 1 (usually the admin). They now have full admin access to your application.

The Fix

Never hardcode secrets. Load them from environment variables instead:

# ✅ backend/utils/security.py
import os

SECRET_KEY = os.environ.get("SECRET_KEY")

if not SECRET_KEY:
    raise ValueError(
        "SECRET_KEY environment variable is not set. "
        "Generate one with: python -c \"import secrets; print(secrets.token_hex(32))\""
    )

Then set it in your local environment (never commit this file):

# In your terminal or a .env file (make sure .env is in .gitignore!)
export SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"

Issue 2: Real RSA Private Key Committed to Repository [CRITICAL]

File: docker-compose.yaml, line 32

# ❌ What you have
GITHUB_PRIVATE_KEY: "-----BEGIN RSA PRIVATE KEY-----\nMIIEpAIBAAKCAQEAtEt+KTSn5ETGVPyMvSK4Kl/JvgPZ0x8Iiy0m1/3cBKwDEwuh\n..."

Why This Is Dangerous

This looks like a real RSA private key, not a placeholder. This is the most critical type of secret leak. A GitHub App private key lets whoever holds it authenticate as your GitHub App and perform any actions it has been granted — reading private repositories, writing code, managing webhooks, accessing organization data, etc.

Real-world scenario: A malicious actor clones your repo (or finds it via a Git scraping bot, which scan GitHub constantly), extracts the key, and uses it to silently exfiltrate code from every private repository your GitHub App has access to. You may never know it happened.

Immediate Actions Required (Do These Now)

  1. Revoke this key immediately — Go to your GitHub App settings → Private keys → Delete this key. It doesn't matter if you fix the code; the key is compromised the moment it touched a git commit.
  2. Assume the key has already been used — Check your GitHub App's audit log for unexpected activity.
  3. Generate a new private key in GitHub App settings after revoking the old one.

The Fix

# ✅ docker-compose.yaml
services:
  backend:
    environment:
      GITHUB_PRIVATE_KEY: ${GITHUB_PRIVATE_KEY}  # Loaded from environment

Store the actual key in a .env file that is never committed:

# .env  (THIS FILE MUST BE IN .gitignore)
GITHUB_PRIVATE_KEY="-----BEGIN RSA PRIVATE KEY-----
MIIEpAIBAAK...
-----END RSA PRIVATE KEY-----"

Verify your .gitignore has:

# .gitignore
.env
*.pem
*.key

For production, use a proper secrets manager (AWS Secrets Manager, HashiCorp Vault
